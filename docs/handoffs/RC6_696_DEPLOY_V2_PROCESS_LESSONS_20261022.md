## Reconciliación con el plan anterior de Deploy V2

Antecedentes: `docs/DEPLOY_V2_ARCHITECTURE.md` y `POROTA_AUDITORIA_CHECKPOINT_2026-09-25.md`, secciones 14–16. El segundo propuso `CACHE ÚTIL → BUILD ONCE → TEST → PROMOTE → VALIDATE → CLEANUP` y un clasificador de cambios. Sus afirmaciones sobre el workflow de septiembre son baseline histórico, no el estado de octubre.

| Propuesta anterior | Estado comprobado al 22/10 | Trabajo necesario |
|---|---|---|
| Build único en CI, imagen exacta, SHA/manifiesto y `docker load` en host. | Implementado en Predeploy/Deploy V2; el artefacto sigue verificándose antes de instalar. | Conservar identidad, no reconstruir en Droplet. |
| Caché BuildKit entre runners y tests independientes solapados. | **No implementado** en el flujo productivo `52843ee8`; PR #709 abierto, dos intentos Predeploy SUCCESS del mismo SHA (22m57s y 21m11s frente a 26m43s). | Dos corridas muestran ahorro neto y cinco recibos nativos exit0/sin OOM; ZIP warm comprobado independientemente; revisar impacto de cuota de cache y gate de identidad antes de incorporar. |
| Diff-aware: docs/tests/GitHub-only sin host; host/systemd-only sin reconstruir imagen. | Parcial: `docs/**` ya está ignorado por trigger push de Deploy V2; otros paths aún fuerzan imagen/deploy. | Clasificador tipado de paths + import closure, árbol runtime separado del árbol fuente, recibo `NO_RUNTIME_CHANGE` y gate negativo que falla ante ruta desconocida. No saltar Predeploy/host por extensión de archivo solamente. |
| Recrear sólo servicios afectados cuando digest runtime no cambia. | Pendiente: la promoción V2 sigue una transacción de observer/dashboard/control plane. | Prueba de identidad/capacidad por servicio y estado del ledger/timers; preservar atomicidad y no declarar VALIDATED_RUNTIME por un deploy parcial. |
| Limpieza postvalidación y preflight de espacio. | Gated por reserva/disk housekeeping y limpieza de imagen candidata no referenciada; no habilita borrado indiscriminado. | Medir bytes/inodos y referencias antes de GC; nunca borrar volúmenes, DB ni evidencia fallida. |

Reutilización del mismo SHA cuando falla algo pequeño: si el fallo ocurre **antes de cualquier mutación del host** y fue transitorio de runner/red/upload, reintentar el mismo job/artefacto exacto después de clasificar el error y comprobar su integridad; no generar un commit ficticio ni repetir build por cambiar sólo un comentario. Si la prueba detecta un bug de código, un recibo inválido o el host ya cambió, se exige RCA y fix-forward con SHA/árbol nuevos, Predeploy completo y nuevo artefacto. El workflow actual todavía no emite un recibo tipado suficiente para automatizar esa elección; implementar y ensayar esa clasificación antes de permitir un atajo de same-SHA. El operador no debe reinterpretar un job FAILED como GREEN por un retry informal.

El PR #709 implementa una parte del plan anterior, no el clasificador completo. Mantener el diff-aware y recreación selectiva en PR posterior con fixture de cada clase y fallo cerrado; el cambio de protocolo de identidad requiere nueva cadena de validación y no se introduce durante el fix-forward #707.
