## SQLite resource accumulation

The 60-second read-only lock capture [38190106380/1](https://github.com/mbalbo2023/Porota-trading/actions/runs/38190106380), artifact 11721257461, ZIP SHA256 `7b79fd902bd53a1cefb0a0ff9112fedcfda3c6dde193ae09e7200c7dd98dd453`, JSON SHA256 `b899dca1daa030ee889b33874e79137593ad1472383248b3340ad62dbdd07358`, attributed eight SHM WRITE observations to observer descendants by actual PID ancestry. Several observer children retained READ locks through all 60 samples. The previous hour of observer logs contained 15 `database is locked` lines (not 15 distinct incidents). A derived analysis of those *same bytes*, [38190390503/1](https://github.com/mbalbo2023/Porota-trading/actions/runs/38190390503), artifact 11720687729, showed the observed SHM WRITE episodes were at most three consecutive seconds. No long writer was proved by this sample.

The changed discriminant, read-only FD trend [38190516003/1](https://github.com/mbalbo2023/Porota-trading/actions/runs/38190516003), artifact 11721691943, ZIP SHA256 `dbe061cbd0a64fee01146e9a830ed6b6cd84eac8429171baab07353e539cd17d`, JSON SHA256 `1b94d1d12c14cad4ca08ccba28aa2359f7823469253cd84d7dbf31da85911378`, measured the same PID 3181085/start_ticks 427173979 with DB FD counts **41, 47, 53, 59, 65** over 120 seconds. The exact argv allowlist [38190755511/1](https://github.com/mbalbo2023/Porota-trading/actions/runs/38190755511), artifact 11721423047, ZIP SHA256 `5819bb47f4d6b7cd9bbe7fd88cd2d573dc12df951a40fabd58ddafd46b52b3f7`, JSON SHA256 `65f4aa3b62d626d602a1e1492a3245b4aef898b3b1d19d78ac733250cb2bafab`, maps that PID to `EXIT_READER` with 67 DB FDs.

The active image's `bv_paper_runtime.py` and `be_paper_engine.py` SHA256 equal the files in the SRE checkout based on production Source, verified by read-only [38190964751/1](https://github.com/mbalbo2023/Porota-trading/actions/runs/38190964751). `bv_paper_runtime._reader_status_write` uses `with sqlite3.connect(store.path, timeout=0.35)` and `run_reader` calls it every five seconds outside market. The SQLite connection context manager commits or rolls back but does not close the connection; a direct local SQLite check verified it remains usable after leaving `with` until explicit `close()`. The observed FD growth is consistent with connections retained pending GC, and this code path is a concrete repeatable resource defect. **It is not yet proved that this defect causes every lock exception.** Other writers, transaction duration and the next market session remain to be tested. A bounded `quick_check(1)` timed out at 85 seconds in run 38161901175, so full integrity remains `NO_VERIFICADO`; do not retry unchanged or mutate WAL.

Fix proposed to G5P owner [#489 comment 6115986467](https://github.com/mbalbo2023/Porota-trading/issues/489#issuecomment-6115986467): explicitly close `_reader_status_write` connections after transaction exit, cover success, busy/rollback and repeated WAITING_MARKET iterations with bounded FD regression, and audit other worker scopes. `bv_paper_runtime.py` and `be_paper_engine.py` are already changed by PR #492; SRE must not write these paths during that ownership. A source fix needs one certified immutable candidate and canonical Deploy V2, followed by runtime FD and lock observations under representative load.
